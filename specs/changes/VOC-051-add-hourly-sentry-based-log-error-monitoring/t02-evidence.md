Evidence for `VOC-051-T02` (`VOC-051-AC-01`…`VOC-051-AC-05`, `VOC-051-AC-07`) and
`VOC-051-T04` (`VOC-051-AC-06`), tests `VOC-051-TEST-02`…`VOC-051-TEST-08`.

This file also carries the three explicit design proposals `tasks.md`'s
`VOC-051-T02` requires the implementer to state rather than leave implicit in

## 1. Open question 1 — GitHub API identity: a GitHub App installation token, not `GITHUB_TOKEN`

**Chosen: a GitHub App installation token** (`actions/create-github-app-token@v1`
with `KARSIFT_BOT_APP_ID` / `KARSIFT_BOT_PRIVATE_KEY`, requesting
`permission-issues: write` only), falling back to `github.token` when those
credentials are absent — the same `steps.app-token.outputs.token || github.token`
shape `karsift-ai-infra`'s `adopt.yml` already uses.

This is not a stylistic preference between the two options the specification
listed. **GitHub does not start new workflow runs from events created with the
default `GITHUB_TOKEN`** (its documented loop-prevention behaviour). An issue
opened with `GITHUB_TOKEN` therefore does not fire `pipeline.yml`'s
`plan-from-issue` job — which is triggered by `issues: opened` with no labels
(`pipeline.yml` lines 153-156) and is the entire reason this workflow files an
issue at all. Picking the "simplest" option here would have produced a workflow
that looks correct, passes every static check, files issues that read perfectly,
and silently never reaches the planner. That failure mode would be invisible
until someone noticed issues accumulating with no `plan-from-issue` run against
them.

The fallback is deliberately honest about this rather than silent: when the App
credentials are missing, the script emits a `core.warning` stating that the
issues it opens will not trigger `plan-from-issue` and that planning must be
started by hand. The run still files the issue — losing the report entirely
would be worse than filing one that needs a manual nudge.

Least privilege is preserved on both paths: the workflow's `permissions:` block
grants `issues: write` and nothing else (no `contents:`, `deployments:`,
`packages:`, or `pull-requests:`), and the App token is minted with the matching
single permission rather than the App's full installation scope.

## 2. Open question 2 — Sentry token scope: `project:read` + `event:read`, and why exactly those

**Recorded scope: an internal-integration token (`vocanova-monitoring-agent`)
scoped to `project:read` + `event:read`, with no write or admin scope on any
resource**, stored as the `SENTRY_API_TOKEN` Actions secret. This matches what
`t00-evidence.md` §3/§4 records the founder as having actually created, and
§1b as having predicted.

Why exactly those two and nothing else:

- The workflow makes exactly one kind of Sentry call:
  `GET /api/0/projects/{org}/{project}/issues/`. Sentry's permission model puts
  issue listing behind its Issue & Event read scope (`event:read`) and project
  resolution behind `project:read`.
- Nothing narrower works. Neither scope alone satisfies that endpoint, so this
  is the minimum sufficient pair rather than a comfortable margin.
- Nothing broader is justifiable. The workflow never resolves, ignores,
  assigns, deletes, or otherwise mutates a Sentry issue, never creates or edits
  a project, and never reads organization members or billing. Every `*:write`
  and `*:admin` scope is therefore unused, and an unused write scope on a
  credential that lives in CI is pure downside.
- An **internal-integration** token rather than a personal token, because the
  Sentry plan has a single user seat (`t00-evidence.md` §1a/§5) and a personal
  token would be bound to it. Rather than a plain organization auth token,
  because that type's scope set is fixed rather than selectable and so cannot be
  narrowed to these two (`t00-evidence.md` §1b).

The token is treated as **required, not optional**: the script's first action is
to assert `SENTRY_API_TOKEN` is present and non-empty and throw if it is not
(`VOC-051-T03`'s explicit requirement — fail loudly, never silently no-op the
way `apps/api`'s optional `SENTRY_DSN` is allowed to). The expected scope is
also documented in the workflow file's own header comment, which is what
`VOC-051-TEST-02`'s preconditions call for.

**Limitation, stated plainly:** this is a record of the scope as configured and
as required by the calls the workflow makes. It is not an independent re-check
of the live token's granted scopes — no Sentry credential exists in the
implementation environment. `VOC-051-TEST-02`'s "inspect the token's actual
granted scopes" step remains a human/founder action against the Sentry UI, as
`t00-evidence.md` §4 item 2 already flagged. Nothing in this task's diff can
substitute for it.

## 3. Open question 4 — "since last check" state: a fixed 90-minute overlapping window, no persisted state

**Chosen: a fixed look-back window of 90 minutes on an hourly schedule, with no
persisted "last checked" marker of any kind** — no workflow artifact, no cache
entry, no committed file. The window is passed to Sentry server-side as
`is:unresolved firstSeen:-90m`.

Reasoning:

- The 30 minutes of overlap absorb a late or dropped cron tick. GitHub's
  scheduled triggers are explicitly best-effort and can be delayed or skipped
  under load; a window exactly equal to the cadence would silently lose every
  issue first seen during a skipped hour.
- Every persisted-state option costs more than it buys here. An artifact or
  cache entry can be evicted or expire, and its absence is indistinguishable
  from "nothing has happened yet" — a stale or missing marker either re-scans
  everything or skips a window, and neither failure announces itself. A
  committed marker file would require `contents: write` on a workflow whose
  entire security posture rests on holding `issues: write` and nothing else,
  and would add a commit to `develop` every hour.
- The overlap is harmless precisely because the duplicate-check index (§4) is
  authoritative rather than best-effort. Re-seeing an already-reported Sentry
  issue is a no-op, so a wider window costs one extra dedup lookup, not a
  duplicate issue.

Efficiency, addressing the previous revision's finding that it paginated all
unresolved issues and filtered client-side: the window is now a server-side
query filter, results are requested `sort=new` (newest first-seen first), and
pagination stops at the first issue older than the window instead of walking the
project's whole unresolved backlog. The client-side `firstSeen` check is kept as
a guard, not as the filter.

**Known gap, not solved by this task:** Sentry silently dropping events after
the Developer plan's account-wide 5,000 errors/month quota is exhausted is
indistinguishable from "no new problems" to this workflow, since it is not an
API error. `t00-evidence.md` §5 raises this and `impact-analysis.md`'s
`VOC-051-R02` covers API errors only. Recorded as a follow-up, deliberately not
fixed inline (it needs a quota/usage query and a distinct alerting decision,
which is outside this task's scope).

## 4. Duplicate-check guard (`VOC-051-AC-04`) — rebuilt to remove the search-index dependency

The previous revision searched GitHub's Search API once per candidate issue for
an `is:open` marker match. Two problems, both fixed:

1. **Search is an eventually-consistent index.** An issue opened minutes earlier
   may not be findable yet, so two runs close together could each conclude the
   same Sentry issue was new. The guard now builds its marker index once per run
   by paginating `issues.listForRepo` and extracting every
   `sentry-issue-id:<id>` marker from the bodies it sees — a direct read of
   repository state, with no index lag between "issue exists" and "guard can see
   it". It is also fewer API calls: one pass over the issue list per run instead
   of one search per candidate.
2. **`is:open` was too narrow for the acceptance criterion.** `VOC-051-AC-04`
   requires that repeated runs "never open a second GitHub issue" for the same
   underlying Sentry issue. The index is now built with `state: "all"`, so a
   Sentry problem whose GitHub issue has already been closed as fixed does not
   produce a second one. (The trade-off — a recurrence after a fix is not
   re-reported automatically — is the behaviour the acceptance criterion asks
   for; a human reopening the closed issue, or a genuinely new Sentry issue ID,
   is the intended path there.)

Three further hardening changes:

- **`concurrency: { group: error-monitoring, cancel-in-progress: false }`.**
  Without it, an hourly run overlapping a manual `workflow_dispatch` could have
  each built its own index and both created an issue for the same problem.
  Runs are serialized, and never cancelled mid-flight while creating issues.
- **The marker string is now identical everywhere it appears.** The previous
  revision's visible "Sentry issue ID:" line used different text from the
  `<!-- sentry-issue-id:... -->` comment, so it would not have matched. The body
  now carries the one canonical marker in the HTML comment and repeats that same
  exact string in a visible footnote asking readers not to edit it.
- **An incomplete index fails the run.** If the issue-list scan hits its
  40-page bound, the script throws rather than proceeding with a partial index
  that would open duplicates.

## 9. Limitations

- No live `workflow_dispatch` run exists for this revision: the workflow does
  not exist on the default branch until this PR merges, and `test-plan.md`
  forbids exercising it against the real Sentry projects or filing throwaway
  issues on the real tracker. §6's verification is stub-driven execution of the
  exact committed script body, which is stronger than inspection but is not a
  live run. The first real scheduled run after merge is the remaining evidence,
  and it should be checked by a human — a run that opens zero issues is
  indistinguishable, from the outside, from one that failed to query anything.
- The live Sentry token's granted scopes were not independently re-verified
  (§2's limitation).
- Whether the GitHub App credentials (`KARSIFT_BOT_APP_ID` /
  `KARSIFT_BOT_PRIVATE_KEY`) are actually present on this repository was not
  verified from the implementation environment; the fallback path and its
  warning exist for exactly that uncertainty. If they are absent, the first
  monitoring run's log will say so explicitly.
- `actionlint` was unavailable (§8).
